## 1. Resumo executivo

O branch entrega um **MVP de multistream local** bem estruturado em camadas:

| Camada | Peças principais |
| --- | --- |
| Catálogo | `StreamPlatform`, limites de ingest, OAuth vs chave manual |
| Persistência | `MultistreamChannelStore` (metadata no `.ini`) + `SecureTokenStore` (chaves/tokens no vault do SO) |
| Contas | `PlatformOAuthClient`, `ConnectedAccountManager`, diálogo de contas |
| Saída | `MultiStreamManager` (fan-out RTMP com encoders compartilhados) |
| UI | `MultistreamChannelBar`, `AddChannelDialog`, `ManualChannelDialog` |
| Qualidade pré-live | `MultistreamPreflight` |
| Chat | `MultiStreamChatAggregator` + `UnifiedChatDock` |
| Testes | `test/product-oauth` (PKCE, catálogo, Credential Manager) |

A revisão documentada em `REVISAO_MULTISTREAM.md` **já corrigiu** os bugs críticos de config divergente, faixas de áudio, WebSocket do Kick, chat YouTube, timeout OAuth, ciclo de vida de `Destination`, build fora do Windows e vários itens de UX/segurança.

O que ainda pesa:

1. **Modelo de saída híbrido** — destinos multistream são *extras* em cima do stream principal do OBS, não o único caminho de “Ir ao vivo”.
2. **Perda de metadados no restore OAuth** — faixa de áudio / VOD somem a cada boot.
3. **Pré-voo incompleto** — sem checagem de upload × N destinos e sem gate de “chave ausente” no botão de stream.
4. **Lacunas de produto do MVP** — wizard de criador, presets 720p/1080p orientados a multistream, e “Go live” único sem jargão de output.
5. **Testes estreitos** — só OAuth/primitives; fan-out, store e preflight sem cobertura automatizada.

## 2. O que está sólido

### Arquitetura

- Separação clara: OAuth **nunca** chega no `MultiStreamManager`; só server + stream key.
- `StreamPlatformConfigSection()` como fonte única de seção de conta (pós-C1).
- `MultistreamChannelStore` com lista N canais, migração do layout legado one-account-per-platform e limite de 32 destinos.
- Stream keys manuais no Credential Manager (`manual-rtmp` / channel id); OAuth keys resolvidas sob demanda e não gravadas no `.ini`.
- Fan-out com `shared_ptr<Destination>` + lista de aposentados (pós-C7): reduz use-after-free com callbacks do libobs.
- Encodes de áudio **posicionais** por faixa OBS (pós-C2), com VOD track só onde o catálogo permite (`supportsVodTrack` → Twitch).
- Pool de threads dedicado (`MultistreamTaskPool`) em vez de saturar o pool global do Qt.
- HTTP OAuth com retry em 429/5xx e validação de host loopback (não só prefixo de URL).
- Preflight de orientação / resolução / fps / bitrate por plataforma.
- Barra de canais com health (congestion, drops, uptime, reconnects) e reconnect por destino.
- Chat: IRC Twitch, WebSocket mascarado Kick, YouTube com Bearer + `pollingIntervalMillis`; desconecta com o dock oculto.

### Segurança e higiene

- Tokens no Windows Credential Manager; stub em não-Windows.
- Wipe de `streamKey` no reconfigure/destruição do manager (ainda não é um tipo `SecretString` completo).
- Cores de chat validadas como `#RRGGBB`; links externos desligados no rich text.
- Client secrets de produto não embutidos; Kick exige proxy de token exchange (ou secret local só em dev).

### UX de produto

- Grid “Adicionar canal” separado em **Entrar** (YouTube/Twitch/Kick) vs **Chave** (Facebook, TikTok, X, Trovo, Custom RTMP).
- Cartões com cor de marca, avatar ou logo Simple Icons, toggle por destino durante a live.
- Diálogo de contas com cancelar + timeout de 5 min.
- i18n `en-US` / `pt-BR` e estilos no tema `Yami.obt` (sem stylesheet local anulado).

## 3. Mapa do fluxo atual (como o código realmente se comporta)

```text
Boot
  └─ MultistreamChannelStore::Load()
       ├─ manuais → key do vault → Configure imediato
       └─ OAuth  → ResolveChannel (refresh + ingest API) em MultistreamTaskPool
                    └─ Configure + BindMultistreamManager → barra

Usuário + (Add channel)
  ├─ OAuth  → MultistreamAccountsDialog → CompleteConnection → Save store
  └─ Manual → ManualChannelDialog → Upsert store

Ir ao vivo (botão Stream do OBS)
  └─ SimpleOutput / AdvancedOutput
       ├─ sobe o streamOutput PRINCIPAL (serviço Settings > Stream)
       └─ se multiStreamManager->HasEnabledChannels()
            └─ Start() cria 1 rtmp_output por destino (encoders compartilhados)

Parar
  └─ para principal + multiStreamManager->Stop()
```

Implicação de produto: **multistream não substitui o stream principal** — ele multiplica RTMP a partir dos mesmos encoders, *depois* que o output principal sobe.

## 4. Achados abertos (ainda no código)

Prioridade: **P0** bloqueia uso real; **P1** bug sério ou risco de produto; **P2** qualidade / roadmap.

### P0 — Modelo “stream principal + extras”

**Onde:** `SimpleOutput.cpp` / `AdvancedOutput.cpp` (após `obs_output_start(streamOutput)`), e o fluxo normal de `StartStreaming` do OBS.

**Problema:** o usuário ainda precisa de um serviço OBS válido em **Configurações → Transmissão**. Os cartões da barra são *adicionais*. Consequências:

1. Upload dobrado se o principal for a mesma plataforma de um cartão (ex.: Twitch no Settings *e* Twitch no multistream).
2. Falha do principal impede o fan-out, mesmo com N canais multistream corretos.
3. O MVP pede “selecionar dois ou mais destinos e ir ao vivo” sem jargão de output — a experiência atual ainda é OBS clássico + barra.

**Sugestão:**

- Curto prazo: se houver ≥1 destino multistream habilitado com credencial, **não exigir** (ou auto-desligar) o serviço principal; ou usar o primeiro destino habilitado como principal e o resto como extras.
- Médio prazo: “Ir ao vivo” = só `MultiStreamManager` (ou um output primário escolhido entre os cartões) + gravação/VCam independentes.
- UX mínima: aviso claro na barra se o serviço principal estiver apontando para a mesma plataforma de um cartão ativo.

---

### P0 — Restore OAuth descarta faixa de áudio / VOD / id estável de loja

**Onde:** `OBSBasic::RestoreMultistreamAccounts` + `ConnectedAccountManager::MakeChannel` / `ResolveChannel`.

No boot, canais OAuth viram só `{platform, accountId, displayName, enabled}`. `ResolveChannel` recria o `MultiStreamChannel` do zero:

- `audioMixIndex` volta a `0`
- `vodTrackEnabled` / `vodTrackIndex` voltam ao default
- qualquer campo persistido no store (exceto id derivado de `platform:accountId`) se perde na memória do manager

O store no disco ainda tem os valores corretos, mas o manager em runtime **não os reaplica** após a resolução de ingest.

**Sugestão:** após `ResolveChannel`, copiar server/key/avatar do resultado e **preservar** do canal carregado do store: `id`, `audioMixIndex`, `vodTrack*`, `enabled`, e opcionalmente `displayName` se o usuário tiver renomeado.

```text
stored = Load()[i]
resolved = ResolveChannel(...)
resolved.audioMixIndex = stored.audioMixIndex
resolved.vodTrackEnabled = stored.vodTrackEnabled
...
```

### P1 — Credenciais OAuth resolvidas só no boot (não no “Ir ao vivo”)

**Onde:** `RestoreMultistreamAccounts`; ausência de re-resolve em `StartStreaming` / preflight.

Se o refresh falhar no boot, a chave expirar no meio do dia, ou o usuário conectar a conta e ir ao vivo antes do pool terminar, o destino fica sem server/key ou com key velha. O MVP pede resolver ingest “imediatamente antes de ir ao vivo”.

**Sugestão:**

1. Passo de **preflight de credenciais** no clique de Stream: para cada canal OAuth habilitado, `ResolveChannel` (com cache curto, ex. 5–15 min).
2. Se falhar, marcar o cartão `Failed` com mensagem acionável e **não** subir só o principal em silêncio.
3. Manter o restore no boot como “esquenta UI”, não como única fonte da verdade.

---

### P1 — Preflight sem capacidade de upload e sem bloqueio

**Onde:** `MultistreamPreflight` (só compara limites de plataforma vs settings).

O MVP lista: *“Preflight checks for upload capacity, missing stream keys, and unsupported settings.”*

Hoje:

| Check | Status |
| --- | --- |
| Orientação / resolução / fps / bitrate por destino | Implementado (advisory/warning na barra) |
| Chave/servidor ausente | Não bloqueia o botão Stream; só falha no `Configure`/`Start` |
| Upload ≥ N × bitrate de vídeo (+ áudio) | **Ausente** |
| Diálogo de confirmação com findings Warning | **Ausente** (só texto na barra) |

**Sugestão:**

- Estimar `requiredKbps ≈ videoBitrate * enabledCount + audioBitrate * enabledCount` (e avisar overhead de RTMP ~5–10%).
- Reusar a ideia do bandwidth test do `AutoConfig`, ou um probe leve opcional.
- No StartStreaming: se houver Warning de preflight ou canal enabled sem credencial, mostrar diálogo “Continuar mesmo assim?” / bloquear.

Bitrate em modo Advanced não é lido (só Simple) — documentar ou extrair do encoder ativo quando possível.

---

### P1 — Falha parcial do fan-out ainda é fácil de perder

**Onde:** `SimpleOutput` / `AdvancedOutput` só `blog(LOG_WARNING, ...)` se `multiStreamManager->Start` falha; `ReportFailure` atualiza a barra, mas o UI principal já mostrou “AO VIVO” no stream principal.

**Sugestão:** toast / `OBSMessageBox` não modal: “Transmissão principal ativa; destinos extras falharam: …”. Se **todos** os extras falharem e o usuário só se importa com a barra, deixar isso explícito.

### P1 — Chat no “first release” vs escopo do MVP

`MVP.md` coloca chat agregado **fora** do first release; o código já tem dock + aggregator (~780 linhas) com complexidade (Pusher, cota YouTube, reconexão).

Isso não é bug, mas:

- Aumenta superfície de falha e manutenção antes do core “ir ao vivo em N destinos” estar à prova de bala.
- Filtros do dock hardcodam Twitch/YouTube/Kick (não seguem o catálogo dinamicamente).
- Uma conexão por plataforma no aggregator: **não escala** se o usuário tiver 2 contas Twitch.

**Sugestão:** tratar chat como flag de build / milestone 1.1; garantir que o Go-live path funcione 100% com o dock desligado. Evoluir o aggregator para N conexões por `channelId`, não por `StreamPlatform` enum.

### P2 — `SecretString` / cópias de stream key

Keys ainda circulam em `std::string` (diálogo, store load, `obs_data` do service, vetor do manager). O manager zera em alguns pontos; cópias intermediárias e o blob interno do libobs service settings não.

**Sugestão (incremental):** tipo thin com wipe no destrutor para o caminho de produto; evitar log de `obs_data` de serviço multistream; limpar `serviceSettings` após `obs_service_create` se a API permitir.

---

### P2 — Dualidade de identidade de conta

Ainda existem seções legadas / fluxo OBS nativo (`YoutubeAuth`, `TwitchAuth`, Settings → Stream) **em paralelo** ao multistream (`MultistreamAccount.*` + store). Risco de o criador conectar YouTube em dois lugares e achar que “é a mesma conta”.

**Sugestão:** no onboarding do produto, esconder ou redirecionar o serviço principal do OBS para o fluxo de canais; documentar a migração.

### P2 — Plataformas manuais e servidor TikTok

Ingest TikTok (`rtmp://push-rtmp-l1-va01.tiktokcdn.com/live/`) e outros defaults do catálogo **mudam com região/conta**. Chave colada com servidor errado = falha opaca.

**Sugestão:** no `ManualChannelDialog`, permitir editar o server (já deve ser possível no custom; garantir nas plataformas nomeadas) e texto de ajuda “use o servidor que o painel da plataforma mostrar”.

## 6. Pontos de atenção de performance e rede

1. **Custo de upload linear em N:** 3 destinos a 6000 kbps ≈ 18 Mbps só de vídeo. A UI deveria mostrar “largura estimada” na barra ou no preflight.
2. **Encoder único:** se TikTok (vertical 30 fps) e Twitch (1080p60) estiverem juntos, um dos dois sofre; o preflight avisa orientação/limites, mas não oferece segundo encode nem canvas vertical paralelo (roadmap).
3. **Resolve no boot:** 3 plataformas × (refresh + ingest) no pool de 3 threads com timeout 30s — ok, mas compete com cold start da UI; preferir lazy + cache.
4. **Chat YouTube:** respeita `pollingIntervalMillis` (bom); ainda assim, com live longa, monitorar cota se escopos extras forem pedidos no futuro.

## 7. Riscos de produto / legal

- **Fork GPL:** distribuição binária exige source correspondente e notices — marco 7 do MVP ainda aberto.
- **Credenciais:** nunca reutilizar client IDs do OBS Project (já documentado em OAUTH_PLATFORMS).
- **Kick token proxy:** peça de infra obrigatória em produção; sem ela o card fica “pending” e o usuário não entende o bloqueio se a mensagem for genérica.
- **APIs não estáveis:** chat Kick via Pusher app id fixo no cliente — risco de quebra unilateral; aceitável para protótipo, frágil para release.

- Barra vazia: CTA único “Adicionar destino” (já existe `+`); evitar jargão “serviço RTMP”.

- Health: traduzir congestion para linguagem humana (“fila de envio alta”) em vez de só número 0–1 se a barra mostrar texto técnico.

## 11. Conclusão

A base técnica do multistream nesta branch está **acima da média de um MVP de fork**: catálogo de plataformas, vault de credenciais, fan-out RTMP com health, preflight parcial e correções sérias da revisão anterior já incorporadas.

O maior desalinhamento não é de estilo de código — é de **produto**: o caminho “Ir ao vivo” ainda é o do OBS (serviço principal) com fan-out colado ao lado, o restore OAuth esquece preferências por canal, e o preflight ainda não cobre o que o MVP promete (upload + chaves). Resolver isso antes de polir chat ou wizard evita treinar o usuário em um modelo que depois precisa ser desaprendido.
